# 粗粒度—细粒度算法与代码梳理

## 结论先行

“整体风险 + 局部服务证据”这个研究假设目前**没有被否定**。现有实现真正的问题是：

1. 前向输出分成了粗、细两支，但底层表示和反向梯度没有真正分工；
2. 同一个服务分数同时承担“该服务是否提供故障征兆”和“该服务是否为根因”两种语义；
3. 一个全局标量 `alpha` 只能决定所有样本整体使用多少局部证据，无法判断某个窗口的局部证据是否可靠。

因此，当前结果更准确地说明：**现有的粗细粒度耦合方式不稳定**，不能说明粗细粒度思想不可行。

## 二、当前算法的数据流

输入为历史窗口：

- 遥测 `X`：`[batch, time, service, feature]`；
- 服务图 `A`：`[batch, time, service, service]`。

### 1. 每个服务的局部历史编码

Metrics、Logs、Traces 按模态分别进入 TCN 和时间注意力：

```text
X_i^metric ─ TCN/attention ─┐
X_i^log    ─ TCN/attention ─┼─ modality fusion ─ h_i^local
X_i^trace  ─ TCN/attention ─┘
```

`h_i^local` 只描述服务 `i` 自己过去若干分钟的状态，尚未进行跨服务传播。

### 2. 服务图交互

使用历史窗口最后一分钟的邻接矩阵执行 GAT：

```text
{h_i^local}, A_t ─ weighted GAT ─ h_i^graph
```

`h_i^graph` 包含邻居服务传入的上下文。随后对所有服务做 mean pooling 和 max pooling，得到系统表示 `g`。

### 3. 粗粒度系统风险分支

```text
g ─ failure head ─ c = [c_normal, c_failure]
```

它直接回答“下一分钟系统是否发生用户可见故障”，不要求指出具体服务。

### 4. 细粒度服务证据分支

每个服务使用三部分信息：

```text
[h_i^local, h_i^graph, h_i^graph - h_i^local]
                    │
              service head
                    │
                   e_i
```

其中 `e_i` 是服务级证据分数。它之所以叫“细粒度”，只因为输出单位从整个系统细化到了每个服务；**这不自动意味着它已经学到了更丰富或正确的因果语义**。

服务分数聚合成系统级局部证据：

```text
E_service = log-mean-exp(e_1, ..., e_N)
e_0       = no-failure head(g)
```

细粒度分支自己的故障判别为 `[e_0, E_service]`，RCA 排名为 `softmax(e_1, ..., e_N)`。

### 5. 粗细粒度融合

当前安全残差版本保留粗粒度预测，仅把局部证据作为残差：

```text
final_failure_logit
    = coarse_failure_logit + alpha * (E_service - e_0)
```

`alpha` 从 0 初始化，所以训练开始时最终预测与原始 LTFP 完全相同。

## 三、当前损失与真实梯度路径

总损失为：

```text
L = L_failure + beta * L_evidence + lambda * L_root
```

- `L_failure`：最终系统故障预测交叉熵；
- `L_evidence`：细粒度证据聚合后的正常/故障交叉熵；
- `L_root`：仅在有根因标签的故障窗口上，对服务分数进行根因排序监督。

当前代码中的实际更新关系如下：

| 损失 | 粗粒度头 | 细粒度头 | 时间编码器 / 模态融合 / GAT |
|---|---:|---:|---:|
| `L_failure` | 是 | 经残差 | 是 |
| `L_evidence` | 否 | 是 | **是** |
| `L_root` | 否 | 是 | **是** |

这是最容易被忽略的问题：`alpha=0` 只保证训练初始时局部证据不进入最终预测，**并不阻止 `L_evidence` 和 `L_root` 改写共享主干**。所以即使残差很小，RCA 监督仍然可能改变粗粒度分支使用的 `g`。

## 四、最可能出问题的模块

### 问题 1：只分了输出头，没有分开表示与梯度

Joint 和 Marginal 使用同一个时间编码器、模态融合和 GAT。Joint 多出的根因排序梯度会一路回到共享主干。

这与实验现象一致：

- OB 上根因监督能够同时改善 AP 和 MRR；
- TT 上根因监督改善了服务排名，但最终 AP 下降；
- TT 的 Joint(0.1) 中，即使只看粗粒度全局分支，AP 也只有 `0.570`，说明负迁移在融合之前已经进入共享表示。

因此，首要问题不一定是融合公式，而可能是**细粒度监督污染了粗粒度表示**。

### 问题 2：一个 `e_i` 被要求表达两件不同的事

当前 `e_i` 同时用于：

1. 判断这个服务是否提供“系统将故障”的预测征兆；
2. 判断这个服务是不是根因。

但症状服务可能非常适合预测故障，却不是根因；根因服务也可能在历史窗口中征兆较弱。这两种服务级语义不完全相同。将它们压成一个标量，会让 AP 与 MRR 互相拉扯。

### 问题 3：`alpha` 是全数据共享的单个标量

当前模型只能学到“总体上使用多少局部证据”，不能表达：

- 某个窗口局部证据清晰，应参与预测；
- 某个窗口多个服务同时异常，局部证据不可靠，应主要相信整体分支。

但是，在解决前两个问题之前，不应直接增加复杂门控，否则门控可能只是在掩盖共享表示的负迁移。

### 问题 4：根因监督存在事件时长偏置

`L_root` 按窗口计算。持续时间更长的故障会重复贡献更多根因梯度，模型可能更偏向长事件或稳定阶段，而不是对每个故障事件等权学习。

### 问题 5：图交互可能混合根因与症状

细粒度证据同时使用 `h_i^local`、`h_i^graph` 和二者差值，但 GAT 后的表示已混入邻居症状。这个设计可能有用，也可能让根因和受影响服务更难区分。目前实验还不足以把它认定为首要问题。

## 五、实验结果应该怎样解读

| 数据集 | 模型 | AP | Hit@1 | MRR | 含义 |
|---|---|---:|---:|---:|---|
| OB | LTFP | 0.836 | 0.778 | 0.880 | 粗粒度基线 |
| OB | Residual-Joint(0.1) | 0.888 | 0.944 | 0.972 | 粗细协同在该数据集成立 |
| TT | LTFP | 0.618 | 0.533 | 0.715 | 粗粒度基线 |
| TT | Residual-Joint(0.1) | 0.560 | 0.533 | 0.684 | 共享训练产生负迁移 |

所以不能得出“粗细粒度不可做”。更合理的结论是：

> 服务级监督确实包含可用信息，但当前把异常证据、根因责任和共享表示绑得过紧，导致收益无法跨数据集稳定复现。

## 六、下一版应先验证什么

下一步不应先加一个更复杂的注意力模块，而应做最小的梯度隔离实验：

1. 共享底层时序编码结果；
2. 在粗、细分支前各加一个很小的独立 adapter；
3. `L_root` 只更新细粒度 adapter 和 RCA 头，不更新粗粒度 adapter；
4. 细粒度证据仍可通过残差参与粗粒度前向预测；
5. 对比完全共享、停止根因梯度、独立 adapter 三种设置。

若只做梯度隔离就能恢复 TT 的 AP，同时保留 MRR 增益，说明主要失败机制已找到；若仍无效，再拆分“异常证据分数”和“根因责任分数”。这样每一步都对应一个可检验的失败机制，而不是继续堆模块。
