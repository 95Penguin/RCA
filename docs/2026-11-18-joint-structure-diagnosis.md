# 完整模型结构复查：局部故障源证据与系统影响证据

本轮只读取现有代码、标签和选中 checkpoint，未改变模型或重新训练。以下均为事后诊断，不作为正式模型改进结果。

## 当前结构的主要假设

Metric TCN 表示与 12 维正常偏差构成同一服务证据 E；系统全局向量查询 E，得到注意力加权的局部表示与偏差。系统头直接读取 `[global, selected E, selected deviation]`；RCA 头读取 `[E, graph state, global, deviation]`。

风险在于：E 受到“哪个服务是根因”的相对排序监督，又被当成“系统将发生用户可感知故障”的证据。实现完整、梯度连通，并不意味着这两个语义已经兼容。softmax 注意力还必须在正常窗口分配总和为 1 的服务权重，本身没有拒绝全部局部证据的含义。

## 固定模型的输入通道检查

在 failure_head 的输入处置零最后 12 维，保留选中 checkpoint 的全部权重、服务证据内部的偏差、注意力、全局表示和最终 RCA 头。

| 数据集 / fold | 原测试 AP | 仅屏蔽系统头直接偏差通道 | 屏蔽系统头全部局部输入 |
| --- | ---: | ---: | ---: |
| OB / 0 | 0.712820 | 0.773314 | 0.638153 |
| OB / 2 | 0.553461 | 0.916063 | 0.949876 |
| TT / 0 | 0.636893 | 0.623776 | 0.598590 |
| TT / 4 | 0.769816 | 0.815761 | 0.719559 |

OB fold 2 的验证 AP 也从 0.921117 变成 0.932192。其测试系统头输入分块的逐维 RMS 约为 global=1.195、service=1.063、deviation=4.549。输入尺度失衡值得关注，但尺度差异本身不能证明因果原因。

这些检查说明直接偏差路径在部分部署中有明显不良影响，而 TT fold 0 又从它受益。把全局/局部输入置零会产生分布扰动，不能当作独立训练的消融，也不能据此按测试折选择屏蔽方式。

## 梯度探针

在每个选中 checkpoint 上，抽样训练折 256 个窗口、batch=32、eval 模式（不改变 BatchNorm / dropout），比较共享参数上系统 CE 与 0.5 倍根因排序 CE 的梯度。仅计算两任务都有梯度的参数交集。

| 数据集 / fold | 梯度余弦均值 | 负余弦 batch 数 / 8 | 根因/预测梯度范数中位比 |
| --- | ---: | ---: | ---: |
| OB / 0 | -0.008765 | 3 / 8 | 0.411434 |
| OB / 2 | 0.053187 | 2 / 8 | 0.085835 |
| TT / 0 | 0.101329 | 4 / 8 | 0.002502 |
| TT / 4 | 0.126300 | 1 / 8 | 1.768693 |

没有观察到四组 checkpoint 一致、强烈的负梯度关系。这个局部探针不能排除训练早期或个别参数层的冲突，但不足以将本次下降统一归因于“根因梯度压倒预测”，更不支持直接以 PCGrad 等优化技巧作为论文主创新。

## 正常原型的语义

原型筛选条件是历史及下一时刻的系统故障标签全为 0。这个标签表示未达到用户可感知影响阈值，不保证局部服务没有故障或没有被注入。

按现有 cases.csv 注入时间，在训练正常参考窗口中，统计完整输入历史均位于注入分钟之后的数量：

| 数据集 / fold | 系统正常参考窗口 | 完整历史在注入后 |
| --- | ---: | ---: |
| OB / 0 | 649 | 179 |
| OB / 2 | 539 | 113 |
| TT / 0 | 579 | 131 |
| TT / 4 | 549 | 117 |

约五分之一到四分之一的系统正常参考窗口位于注入之后。注入之后不等于故障一直活跃；这里不能自动标成局部异常。但已经足以说明“系统无影响的正常状态”与“注入前的局部健康状态”不是同一个定义。

本数据确有训练用元数据：`cases.csv` 包含 root_service、fault_type、injection_utc；next_minute_labels.csv 含 pre/mixed/post 和真实影响标签。可以研究训练中区分两种语义，不必向部署模型输入注入时间、case_id 或真实根因。

## 建议收敛的研究方向

把问题改为：怎样利用服务故障源证据预测未来的系统影响，同时避免把无业务影响的局部异常当成系统故障？

1. 源证据：Metric 变化及相对局部健康参考的偏差，服务于根因区分。
2. 影响证据：历史业务时延、错误、请求量和调用上下文，服务于下一分钟系统影响判断。
3. 条件化交互：由影响上下文决定源证据如何参与系统风险；不将原始偏差直接接到系统分类器。
4. 监督约束：训练折中 post-injection 但未发生影响的窗口，是系统预测的重要负例；若有充分的注入持续时间与状态记录，可以形成“源存在、影响未出现”的训练约束。仅有注入起点时，应使用弱标签或排除不确定时段，不能把所有 post 窗口视为持续故障。
5. 与未来系统影响匹配的局部证据，才能反过来辅助预测性 RCA。两个任务保持独立输出语义，所有网络仍可从头端到端训练。

这是候选方法路线，不是已经验证的新颖方法。根因与症状、时空解耦已有相关工作；潜在区别应放在预测任务中“局部故障状态—未来系统影响”的监督和交互机制，不能只是给注意力换名字。

## 文献边界

- [DeST 原文](https://netman.aiops.org/wp-content/uploads/2025/11/DeST_CameraReady.pdf)：将时间模式与空间关系区别利用，讨论空间噪声对异常检测的影响。它的任务是当前异常检测与定位，不能直接把该结论移植到下一分钟预测。
- [Topo-MFP，2026](https://link.springer.com/article/10.1007/s44443-026-01193-5)：已经讨论局部异常、传播症状和源定位，并构建诊断传播图。因此单独提出“区分根因和症状”不能作为新颖性声明。

## 决策边界

工程层先把直接偏差连接视为需要修正的路径。方法层只推进一个“源—影响区分”原型，重点比较同一局部异常在有/无系统影响情况下如何被处理。停止继续叠加图、原型、门控和复杂损失；新设计必须对上述具体矛盾给出可训练的定义。效果和创新性都需要后续确认，不能承诺发表或保证指标提高。
