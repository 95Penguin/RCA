# CPCA、反事实和 operation：按当前实现理解

## 四个词

- 请求：用户发起的一次访问或操作。
- trace：这次请求经过各服务时留下的一整套调用记录。
- span：其中一次调用，含服务、接口名、父调用、开始和结束时间。
- 入口 operation：这次请求的入口类别，当前用 `(入口服务, 入口 span 的 operationName)` 作为键。

每个内部 span 也有自己的 operationName，供健康参考匹配使用；论文中“按 operation 汇总”则特指入口 operation，二者不要混淆。

当前 OB 的入口键只有 `(frontendservice, frontend)` 一个，埋点没有在这个键上区分浏览/下单等业务。
当前 TT 有 17 个入口键，例如 `POST /api/v1/users/login` 与不同的 GET 查询接口。
这些键是按当前入口规则和特征表得到的，不代表所有数据集天然具有相同字段、相同细粒度。
只有指标的数据集无法运行当前 CPCA；有 trace 的数据集仍需适配入口规则、接口名、时间单位和父子关系。
单入口时 operation 汇总自动退化为该入口内部的服务责任排序，不会凭空产生业务区分。

## CPCA 的计算

1. 找出唯一业务入口，检查可用的串行调用树。并行、父子时间关系不合法等请求按规则排除。
2. 把入口耗时拆成本地账本分量和调用间隙。每个间隙只计一次，当前规则将进入边的间隙分给 callee。
3. 从初始健康请求构建同类分量的正常参考。
4. 对服务 B，把 B 负责的分量替换成正常参考，其他服务分量保持观测值，计算模型内入口耗时。
5. 原始入口耗时减去替换后耗时，取正值，得到 B 的恢复贡献。
6. 对同一入口 operation 的请求汇总，以入口耗时归一化；多个入口 operation 等权汇总形成服务排名。

例子只展示已分解账本：一条请求 200ms，A/B/C 分量为 20/150/30ms；B 的健康参考为 50ms。
替换 B 后入口模型耗时为 20+50+30=100ms，因此 B 的正向恢复贡献为 100ms。
这些数字是已经分配后的账本分量，不是直接把各层嵌套 span 的总耗时相加。

“反事实”指在模型里问“如果 B 的分量正常，结果会怎样”，没有真正向运行系统执行修复。
等待归属、请求结构保持不变、健康参考可代表正常状态等都是假设。
`local` 是账本残差，不是 CPU 测量；gap 不一定都是物理网络或排队等待。
入口耗时守恒不意味着截零后的各服务恢复贡献之和等于入口总体异常延迟。

## 与预测的关系

原方法：过去五分钟遥测预测下一分钟；告警时用 CPCA 输出当前可见 trace 的责任排序。
本次试验：把过去五分钟已经可获得的 CPCA 责任分和有效标记加入原预测器输入。
如果试验有效，可以说预测与定位共享责任证据；仍不能说 CPCA 完整解释了神经网络决策或识别了真实修复因果效应。
